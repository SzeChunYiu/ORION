# Development packet — issue #102 P5 protected hidden-cause suite freeze

## Development question

How can the host freeze the P5 hidden-cause benchmark before outcomes while preventing candidate-visible artifacts from disclosing protected root truth, fresh-transfer task contents, evaluator surfaces, rubrics, or retained harmful/null variants?

## Atomic fibres

1. bind all eight registered root-cause families;
2. keep root truth outside candidate-visible material;
3. bind fresh payload bytes/content without publishing them;
4. prove each fresh task changes a preregistered independent axis (task/domain/model/environment);
5. keep motivating/replay identities disjoint from fresh identities;
6. bind evaluator identity before candidate generation;
7. retain every declared negative/null/harmful variant;
8. keep allowed candidate write surfaces disjoint from protected surfaces;
9. produce deterministic content-addressed split/suite commitments;
10. never let a freeze artifact claim empirical success or self-promotion authority.

## Incumbent mechanics and negative history

The P5 protocol is already `DESIGN_FROZEN` and explicitly keeps final execution identities `UNBOUND`. Issue #8/#76 state that repository-only tests cannot substitute for real provider/protected-evaluator evidence. The existing readiness failure history also forbids caller/internal booleans from manufacturing an external PASS. Therefore the freezer must produce commitments only, never a readiness verdict.

## Parent-domain recovery

The design uses standard content-addressed manifests plus a salted commitment for the eight-valued protected root label. A plain hash of one of eight public enum values would be brute-force disclosure, so every case must carry a unique protected nonce that remains in the evaluator-held opening material.

## Saturation assessment

The bounded question is not “is the benchmark scientifically valid?” but “can a prospective private suite be frozen without leaking the protected variables or laundering freshness?” The implementation is saturated when every protected datum is either absent from the candidate packet or represented only by a content commitment, and when mutations/omissions of protected payloads fail closed.

## Challenge to saturation basis

A superficially content-addressed design can still leak root truth by hashing a low-entropy label; can call DATA/TOOL changes “fresh” despite the issue requiring a task/domain/model/environment shift; can silently drop orphaned harmful variants; or can overlap candidate write authority with evaluator surfaces. Hostile tests target each of those shortcuts.

## Miss hypotheses

- schema-valid JSON could still violate cross-case uniqueness or coverage;
- fresh-task content hashes could be declared without matching protected payloads;
- fresh IDs could collide with replay IDs;
- a public commitment could disclose low-entropy truth;
- a candidate packet could accidentally inherit protected fields during refactoring;
- a frozen suite could omit one of the eight causal families yet look complete locally.

## Reopen triggers

Reopen this design if: the final protocol changes its root-cause taxonomy or freshness axes; a protected evaluator requires keyed commitments/signatures rather than hashes; baseline execution requires candidate access to currently hidden fields; or an external review demonstrates that the public commitment materially leaks protected information.

## Frozen implementation hypothesis

A stdlib-only `orion.study.p5.freeze` module can validate a private suite and deterministically derive (1) a candidate-safe packet and (2) a protected commitment manifest. It must require all eight families, unique hidden-label nonces, content-matching fresh payloads, at least one TASK/DOMAIN/MODEL/ENVIRONMENT change per fresh task, retained negative variants, and disjoint candidate/protected surfaces. Neither output may increase empirical authority above `CANNOT_CHECK`.
