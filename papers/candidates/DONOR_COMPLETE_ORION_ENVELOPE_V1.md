# Donor-complete ORION envelope V1

**Date:** 2026-08-18  
**Programme:** ORION-16–ORION-18 theory closure  
**Rule:** engulf before narrowing.

## 1. Purpose

The ORION-16–ORION-18 programme does not treat nearest work as a boundary that ORION must avoid. Strong prior mechanisms are treated as **donors**. ORION should absorb each donor's useful structure faithfully, preserve its native judgments in the donor's own regime, and then test whether a common envelope yields new cross-structure theorems, safer composition, broader task coverage, lower inconsistency, or better auditability.

A donor is not "beaten" merely because ORION contains more fields. The comparison hierarchy is:

1. donor-native system;
2. ORION embedding of that donor with all other coordinates inert;
3. ORION composite on a task requiring multiple donor structures;
4. a **donor-product super-baseline** containing the same donor mechanisms with the strongest reasonable interfaces;
5. ablations of the ORION envelope that remove one common structure or preservation rule.

Only levels 3–5 can support a claim that integration matters.

## 2. Common envelope

The shared ORION-16–ORION-18 object is

\[
\mathcal E=(S,\mathsf{Eff},\mathsf{Dep},\mathsf{Prov},\mathsf{Obl},\mathsf{Auth},\mathsf{Rep},\mathsf{Goal},\mathsf{Hist},\mathsf{Inv}),
\]

with:

- `S`: typed scientific state;
- `Eff`: requested/handled/committed effects;
- `Dep`: computational, evidential and authorization dependency structures;
- `Prov`: content identity and provenance;
- `Obl`: hard/soft scientific obligations;
- `Auth`: grants, blockers, coercions, freshness and protected roots;
- `Rep`: active representation/chart/ontology and transformations;
- `Goal`: active objectives and satisfaction semantics;
- `Hist`: immutable positive and negative history;
- `Inv`: non-compensatory invariants.

The envelope does not assume these dimensions are new. Its scientific question is whether the **interfaces among them** admit reusable laws that are absent when each subsystem is treated independently.

## 3. Preservation ladder

A change may preserve different layers independently:

\[
P_0=\text{identity},
\quad
P_1=\text{computation/support},
\quad
P_2=\text{evidence meaning},
\quad
P_3=\text{target-obligation discharge},
\quad
P_4=\text{commit authority}.
\]

The envelope never silently promotes a lower preservation witness into a higher one.

Already closed countermodels establish:

\[
P_1\not\Rightarrow P_3,
\qquad
P_2\not\Rightarrow P_3,
\qquad
P_3\not\Rightarrow P_4.
\]

The scientific task of the envelope is to state the explicit transport/coercion witnesses required for any valid upward step.

## 4. ORION-16 donor engulfing

### 4.1 Truth-maintenance / ATMS

**Imported structure**
- justification/dependency graphs or support families;
- invalidation after changed assumptions;
- preservation of independently supported beliefs/environments.

**ORION embedding**
- dependency nodes/edges map into `Dep`;
- certified scientific claims add `Obl`, `Prov` and `Auth` fields that may be inert in the donor-native special case.

**Composite-only pressure**
- changed certified roots must reopen even if strict descendant closure excludes roots;
- a computationally unaffected descendant may still lose scientific certification if a hard validation obligation or authorization premise changed;
- preservation requires an explicit proof at the relevant preservation layer.

### 4.2 Self-adjusting / incremental computation

**Imported structure**
- dynamic dependence/change-propagation graph;
- incremental update rather than full recomputation;
- from-scratch consistency as the native correctness target.

**ORION embedding**
- computation dependencies map to `Dep`;
- change propagation becomes a mechanic/effect with universal scientific authority in the donor-native special case.

**Composite-only pressure**
- from-scratch computational consistency does not entail preservation of scientific certification or commit authority;
- ORION-16 typed-erasure separation constructs equal bare computations with different admissibility.

### 4.3 Effect systems / ETAS

**Imported structure**
- typed effect rows;
- requested/handled/denied/committed events;
- trace-visible policy checks;
- residual obligations.

**ORION embedding**
- effect rows map to `Eff`, persistent traces to `Hist`, residual obligations to `Obl`.

**Composite-only pressure**
- committed effects can stale dependent scientific certificates;
- residual scientific obligations cannot disappear because later computation succeeds;
- effect admissibility may depend on provenance and scientific-authority roots outside the effect language.

### 4.4 FAVA / evidence-backed authorization

**Imported structure**
- permission IR/graph;
- contextual/data-flow dependencies;
- deterministic pre-effect authorization.

**ORION embedding**
- permission evidence and dependencies map to `Auth`, `Prov`, `Dep`.

**Composite-only pressure**
- an effect may be security-authorized while its scientific obligation is unresolved;
- revoking scientific evidence can invalidate a scientific certificate even when the generic action permission remains valid.

## 5. ORION-17 donor engulfing

### 5.1 Fixed graph / Search-on-Graph

**Imported structure**
- observe-then-navigate iterative graph search;
- schema-sensitive local edge choice.

**ORION embedding**
- fixed chart with atlas transformations disabled.

**Composite-only pressure**
- route/task stopping remains separate from representation/objective closure;
- evidence gathered in one chart must be re-evaluated if the obligation semantics change.

### 5.2 POMDP / belief-space information gathering

**Imported structure**
- partial observability;
- belief updates;
- value-of-information action selection.

**ORION embedding**
- belief state maps to navigation state `b`; utility ranks admissible navigation actions.

**Composite-only pressure**
- expected value or low information gain does not establish scientific task completeness;
- censored/open mandatory obligations remain non-compensatory.

### 5.3 Planning abstraction / homomorphism

**Imported structure**
- abstraction/refinement maps;
- conditions preserving plans/reachability or generalized-planning solutions.

**ORION embedding**
- established abstraction-preservation facts instantiate the relevant components of the ORION-17 transport witness `Pi`.

**Composite-only pressure**
- plan preservation does not automatically preserve evidence identity, scientific coverage, goal meaning or closure authority.

### 5.4 Schema evolution / lenses / ontology mappings

**Imported structure**
- bidirectional or partial transformations;
- round-trip / information-preservation laws;
- schema/ontology correspondence.

**ORION embedding**
- data/semantic preservation witnesses map into `Rep` and the semantic part of `Pi`.

**Composite-only pressure**
- preserving data or semantic correspondence does not establish that the transformed scientific obligation is discharged.

### 5.5 Goal evolution / SAGA

**Imported structure**
- outer-loop objective generation/evolution;
- inner-loop optimization against the current objective.

**ORION embedding**
- objective versions map into `Goal`; objective mutations are atlas transformations.

**Composite-only pressure**
- identical evidence may satisfy the old objective and fail the new one;
- goal change therefore requires evidence-versus-closure transport rather than automatic inheritance.

### 5.6 Self-evolving world models

**Imported structure**
- deployment-time revision from prediction/observation mismatch;
- episodic/semantic memory;
- selective foresight.

**ORION embedding**
- parameter/model update with fixed state vocabulary is intra-chart evolution; representation change is inter-chart evolution.

**Composite-only pressure**
- not every model update licenses a topology change;
- evidence/closure transport depends on which semantic distinctions and obligation predicates changed.

## 6. ORION-18 donor engulfing

### 6.1 Authorization / trust management / proof-carrying authorization

**Imported structure**
- authorization queries and proof of policy compliance;
- delegation, scope narrowing, revocation;
- credentials/policy roots.

**ORION embedding**
- grants/proofs map into `Auth` and authorization support into `Dep`.

**Composite-only pressure**
- a valid generic permission does not discharge an independent scientific obligation required by the effect semantics.

### 6.2 UCON / ongoing authorization

**Imported structure**
- ongoing decisions rather than a single pre-check;
- obligations/conditions;
- mutable attributes and continuity decisions.

**ORION embedding**
- commit-time freshness and mutable authority state map into `Auth` and `Hist`.

**Composite-only pressure**
- freshness of generic permission still does not prove target scientific discharge.

### 6.3 Multi-authority and propagation systems

**Imported structure**
- multiple authority sources;
- delegation/propagation across agents/components;
- temporal validity/stale-authorization controls.

**ORION embedding**
- authority sources and propagation edges become typed grants/coercions.

**Composite-only pressure**
- source-domain success or permission must not become target-domain scientific authority without an explicit full-type coercion/discharge rule.

### 6.4 Agent abstention

**Imported structure**
- paired act/abstain competence;
- recognition that post-hoc abstention is not equivalent to not acting.

**ORION embedding**
- non-action terminals map to `DENIED`, `CANNOT_CHECK`, resource `DEFER`, or route/task stop according to cause.

**Composite-only pressure**
- the reason for non-action determines what can be repaired or retried; the terminals are not interchangeable.

### 6.5 Provenance / execution provenance

**Imported structure**
- content/source lineage;
- process trace and action evidence;
- attribution/auditability.

**ORION embedding**
- provenance maps directly to `Prov` and derivation lineage in `Dep`/`Hist`.

**Composite-only pressure**
- provenance is a premise of some scientific discharges and revocations rather than a generic correctness score.

## 7. Donor-product super-baseline

The strongest comparison is not any individual donor. Define

\[
\mathcal P_{donor}=TMS\times SAC\times Effect\times Auth\times Navigation\times Abstraction\times Goal\times Provenance
\]

with the best reasonable cross-module adapters.

There are three scientifically distinct possibilities.

### Case A — ORION beats individual donors, ties the donor product

Interpretation: the main contribution is **integration and a common scientific interface**, not superior expressivity. This can still matter if the common envelope reduces interface inconsistency, proof duplication, audit complexity or maintenance defects, but those benefits must be measured.

### Case B — ORION beats the donor product on a protected cross-structure task

A valid strong claim requires identifying the missing law/interface in the donor product, freezing it prospectively, and showing that adding exactly that ORION law closes the gap without weakening donor-native behavior.

### Case C — donor product matches or dominates ORION on all scientific and engineering measures

Then the envelope is a useful taxonomy/specification layer but does not justify a separate superiority claim. The relevant paper must narrow or merge.

## 8. Cross-structure challenge families

The programme must attempt to create tasks no single donor dimension can solve alone:

1. **repair + authority:** a changed state requires selective recomputation, but only some recomputed outputs retain scientific certification;
2. **effect + reopening:** a correctly typed committed action introduces a new residual that reopens a previously closed claim;
3. **representation + obligation:** raw evidence survives a chart refinement while the target scientific obligation changes;
4. **goal evolution + provenance:** a new objective can reuse some evidence but not the old closure certificate;
5. **authorization + scientific discharge:** generic action permission is valid but scientific assertion/merge/stop obligations remain unresolved;
6. **revocation + alternative support:** one evidence lineage is revoked while an independent complete derivation should preserve the certificate;
7. **history + policy:** two current-state-equivalent executions differ in later admissibility because a policy is chronology-sensitive;
8. **censoring + resource stop:** the system must stop acting under resource exhaustion without laundering that into task completeness.

Every challenge requires matched no-alarm controls.

## 9. Performance dimensions

"Outperform" is not a single scalar. The envelope should be evaluated on a non-compensatory panel:

- donor-native decision fidelity;
- unsafe scientific authorization rate;
- stale-certificate retention rate;
- unnecessary reopening/reset rate;
- unnecessary refusal rate;
- clean authorized coverage;
- obligation-discharge accuracy;
- revocation precision/recall under alternative derivations;
- premature task-closure rate;
- representation-change benefit and harmful-reframe rate;
- provenance/audit completeness;
- interface inconsistency count;
- proof/trace size and verification cost;
- resource cost under matched capability budgets.

A gain in one coordinate cannot compensate for violating a protected safety/scientific-authority coordinate.

## 10. Theory-completion rule

ORION-16, ORION-17 and ORION-18 may each close their mathematical theory while this envelope remains under experimental pressure. Literature overlap is not a reason to remove a donor mechanism from ORION. It is a reason to:

1. acknowledge ownership;
2. embed it faithfully;
3. test the larger composite;
4. compare against the donor-product super-baseline;
5. retain only claims that survive.

This is the ORION "engulf before narrowing" rule.
